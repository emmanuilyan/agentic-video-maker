# Оркестрация агента: роли, состояния, шлюзы и передача данных

## Цель файла

Даже если работу выполняет один агент, полезно разделять её на специализированные роли. Это предотвращает ситуацию, в которой одно и то же решение одновременно придумывается, исполняется и само себя принимает.

Этот файл определяет:

- роли;
- владельцев производственных артефактов;
- конечный автомат процесса;
- допустимую параллельность;
- формат передачи результатов;
- маршруты возврата при ошибках;
- правила изменения утверждённых решений.

---

## 1. Базовый принцип управления

Каждый этап получает ограниченный вход, создаёт конкретный артефакт и заканчивается решением шлюза.

```text
вход → работа роли → проверяемый артефакт → шлюз → следующий этап или возврат
```

Не передавай между ролями только свободный пересказ. Передавай структурированные документы с наблюдаемыми данными и статусом утверждения.

## 2. Роли

## 2.1. Director / Coordinator — координатор

Отвечает за:

- контракт сцены;
- ограничение сложности;
- порядок этапов;
- состояние процесса;
- разрешение конфликтов;
- утверждение change request;
- финальное решение о выпуске.

Не должен:

- самовольно подменять вывод исследователя;
- вносить незаписанные изменения в кадры;
- пропускать шлюзы ради скорости.

Артефакты:

- `scene_contract.md`;
- `project_state.md`;
- `change_log.md`.

## 2.2. Source Researcher — исследователь источников

Отвечает за:

- поисковые запросы;
- первичные и профессиональные источники;
- референсы движения, материала и постановки;
- provenance;
- лицензии для прямых исходников;
- таймкоды и наблюдения.

Не принимает окончательных постановочных решений.

Артефакт:

- `research_dossier.md`.

## 2.3. Reference Analyst — аналитик референсов

Отвечает за:

- инварианты, переменные и причины;
- фазы движения;
- timing и spacing источников;
- точки отслеживания;
- материальную подпись;
- противоречия между источниками;
- степень уверенности.

Артефакт:

- `reference_synthesis.md`.

## 2.4. Scene Planner — постановщик сцены

Отвечает за:

- граф сцены;
- камеру;
- композицию;
- коридор действия;
- паспорта объектов;
- свет;
- тени;
- перекрытия;
- мастер-кадр;
- `scene_lock`.

Артефакт:

- `scene_blueprint.md`.

## 2.5. Motion Planner — планировщик движения

Отвечает за:

- длительность;
- экспозиции;
- фазы;
- ключевые позы;
- breakdowns;
- spacing;
- дуги;
- контакт;
- деформацию;
- secondary action;
- план блокинга.

Артефакт:

- `timing_sheet.md`.

## 2.6. Frame Executor — исполнитель кадров

Отвечает за:

- создание мастер-состояния;
- ключевые кадры;
- блокинг;
- промежуточные состояния;
- тени и перекрытия;
- имена файлов;
- карту экспозиций;
- запись дельт.

Артефакты:

- `frame_manifest.md`;
- уникальные состояния;
- собранная последовательность.

## 2.7. Continuity Auditor — аудитор непрерывности

Отвечает за:

- статические маски;
- tracking points;
- drift;
- flicker;
- chatter;
- pops;
- scale breathing;
- texture crawl;
- contact lock;
- границы пересоздаваемых участков.

Не исправляет кадры молча. Он создаёт дефектную запись и возвращает её исполнителю.

Артефакт:

- `continuity_report.md`.

## 2.8. Final Reviewer / Rights Reviewer — финальный рецензент

Отвечает за:

- все проходы QC;
- тяжесть дефектов;
- техническую сборку;
- полноту provenance;
- проверку условий прямого использования;
- финальное решение.

Артефакт:

- `qc_report.md`.

## 3. Единое состояние проекта

Все роли читают `project_state.md`. Только координатор меняет основной статус.

Допустимые состояния:

```text
intake
research
research_review
reference_synthesis
synthesis_review
scene_design
scene_lock_review
blocking
blocking_review
motion_refine
frame_finaling
temporal_review
repair
final_qc
accepted
rejected
```

Переходы:

```text
intake
  → research
  → research_review
  → reference_synthesis
  → synthesis_review
  → scene_design
  → scene_lock_review
  → blocking
  → blocking_review
  → motion_refine
  → frame_finaling
  → temporal_review
  → final_qc
  → accepted
```

Состояние `repair` содержит ссылку на этап возврата. `rejected` используется, только если контракт противоречив, исходники незаконны для требуемого прямого использования или результат невозможно привести к контракту без полного нового задания.

## 4. Владение артефактами

| Артефакт | Владелец | Кто проверяет | Кто может изменить после утверждения |
|---|---|---|---|
| `scene_contract.md` | Coordinator | все роли на непротиворечивость | только Coordinator через change request |
| `research_dossier.md` | Source Researcher | Reference Analyst, Rights Reviewer | Source Researcher |
| `reference_synthesis.md` | Reference Analyst | Scene Planner, Motion Planner | Reference Analyst через change request |
| `scene_blueprint.md` | Scene Planner | Motion Planner, Continuity Auditor | Scene Planner через change request |
| `timing_sheet.md` | Motion Planner | Frame Executor, Final Reviewer | Motion Planner через change request |
| `frame_manifest.md` | Frame Executor | Continuity Auditor | Frame Executor |
| `continuity_report.md` | Continuity Auditor | Coordinator, Frame Executor | Continuity Auditor |
| `qc_report.md` | Final Reviewer | Coordinator | Final Reviewer |

Ни одна роль не должна молча редактировать чужой утверждённый артефакт.

## 5. Версии и утверждения

Каждый основной файл содержит:

- идентификатор сцены;
- номер версии;
- дату обновления;
- владельца;
- статус: `draft`, `in_review`, `approved`, `superseded`;
- список зависимых артефактов;
- краткое описание изменений.

Полностью заполненный пример:

```yaml
scene_id: shot01_paper_plane
artifact: scene_blueprint.md
version: 1.2
updated: 2026-09-01
owner: Scene Planner
status: approved
depends_on:
  - scene_contract.md@1.0
  - reference_synthesis.md@1.1
supersedes: scene_blueprint.md@1.1
change_summary:
  - карандаш смещён на 20 нормализованных единиц влево
  - увеличен вертикальный зазор над препятствием
  - камера, свет и паспорта объектов сохранены
```

При обновлении upstream-артефакта зависимые документы получают статус `needs_review`, даже если их содержимое пока не менялось.

## 6. Шлюзы и решения

## 6.1. Research gate

Вход:

- `scene_contract.md`.

Выход:

- `research_dossier.md`.

Проходит, если:

- собраны все обязательные классы референсов;
- для каждого источника указана роль;
- есть таймкоды или конкретные страницы;
- права прямых исходников проверены;
- поиск достиг условия остановки.

При провале: возврат Source Researcher с конкретным недостающим вопросом.

## 6.2. Synthesis gate

Вход:

- `research_dossier.md`.

Выход:

- `reference_synthesis.md`.

Проходит, если:

- наблюдения отделены от решений;
- определены фазы, траектория и материал;
- противоречия разрешены;
- неопределённости перечислены;
- модель достаточна для постановки.

При провале: либо дополнительный поиск, либо переработка синтеза.

## 6.3. Scene lock gate

Вход:

- контракт;
- синтез референсов.

Выход:

- `scene_blueprint.md`;
- мастер-кадр.

Проходит, если:

- весь акт помещается;
- контакт виден;
- паспорта объектов устойчивы;
- камера, фон и свет зафиксированы;
- тени имеют правила.

При провале: возврат Scene Planner. Если причина в недостатке знаний, возврат на исследование.

## 6.4. Blocking gate

Вход:

- `scene_blueprint.md`;
- `timing_sheet.md`;
- ключевые позы.

Выход:

- `blocking_review.md`.

Проходит, если:

- действие читается;
- timing и spacing работают;
- контакт и финал присутствуют;
- нет необходимости менять `scene_lock`.

При провале:

- timing/spacing → Motion Planner;
- скрытый контакт/нехватка места → Scene Planner;
- неверная физика → Reference Analyst или Source Researcher.

## 6.5. Temporal gate

Вход:

- финальные уникальные состояния;
- `frame_manifest.md`.

Выход:

- `continuity_report.md`.

Проходит, если:

- глобальные инварианты стабильны;
- drift и flicker отсутствуют;
- контакты корректны;
- тени согласованы;
- все дефекты исправлены.

При провале: Frame Executor получает диапазон пересоздания и эталонные якоря.

## 6.6. Final gate

Вход:

- все артефакты;
- финальная последовательность.

Выход:

- `qc_report.md`.

Проходит только по правилам `08_QUALITY_CONTROL.md`.

## 7. Пакет передачи между ролями

Каждая передача содержит:

1. идентификатор сцены;
2. текущее состояние;
3. входные версии;
4. утверждённые инварианты;
5. конкретную задачу роли;
6. обязательный формат результата;
7. критерии готовности;
8. известные риски;
9. запреты;
10. маршрут возврата при невозможности выполнить задачу.

### Полностью заполненный пакет для Motion Planner

```yaml
scene_id: shot01_paper_plane
state: scene_lock_review
input_versions:
  scene_contract: 1.0
  research_dossier: 1.1
  reference_synthesis: 1.1
  scene_blueprint: 1.2
approved_invariants:
  camera: статичная, боковая, наклон вниз 12 градусов
  frame: 1920x1080, 16:9, 24 fps
  background: однородный теплый белый
  actor: красный бумажный самолетик с постоянными складками и меткой
  obstacle: неподвижный синий карандаш
  light: один мягкий источник слева сверху
assignment:
  - построить трехсекундное движение самолетика слева направо
  - включить короткую подготовку, дугу, касание крыла с карандашом и посадку
  - использовать двойки как основной режим и единицы вокруг контакта
required_output:
  - timing_sheet.md
  - таблица ключевых поз
  - схема spacing
  - список tracking points
  - план блокинга
acceptance:
  - 72 выходных кадра
  - один ясно читаемый контакт
  - камера и карандаш неподвижны
  - финальный hold не менее 8 кадров
  - бумага деформируется локально не более чем на 4 процента длины крыла
known_risks:
  - стробирование при снижении
  - скрытый контакт крыла с карандашом
  - ощущение плавания при неверной тени
forbidden:
  - движение камеры
  - вращение карандаша
  - добавление частиц и текста
  - изменение цвета или числа складок самолетика
failure_route:
  hidden_contact: Scene Planner
  unknown_material_behavior: Reference Analyst
  insufficient_duration: Coordinator
```

## 8. Change request

Изменение утверждённого решения оформляется отдельно.

Обязательные поля:

- причина;
- затронутый артефакт;
- старое значение;
- новое значение;
- какие downstream-артефакты становятся устаревшими;
- риски;
- решение координатора.

### Полностью заполненный пример

```yaml
change_id: CR-004
scene_id: shot01_paper_plane
requested_by: Motion Planner
reason: в блокинге правое крыло перекрывает карандаш до фактического контакта, из-за чего момент касания не читается
artifact: scene_blueprint.md@1.1
old_value: центр карандаша x=625, y=695
new_value: центр карандаша x=605, y=695
unchanged:
  - камера
  - масштаб объектов
  - свет
  - траектория старта и финала
invalidates:
  - timing_sheet.md@1.0
  - blocking_sequence@0.2
risks:
  - потребуется сдвинуть контактные координаты на 18–22 единицы влево
  - финальный зазор нужно проверить повторно
decision: approved
approved_by: Coordinator
resulting_versions:
  scene_blueprint: 1.2
  timing_sheet: needs_review
  blocking_sequence: superseded
```

Незарегистрированное изменение `scene_lock` считается дефектом процесса.

## 9. Параллельная работа

### Разрешена

После утверждения контракта параллельно можно:

- искать реальное движение;
- искать материальные референсы;
- искать композиционные референсы;
- проверять открытые архивы и лицензии;
- собирать терминологию.

После `scene_lock` параллельно можно:

- готовить паспорта статических слоёв;
- уточнять shadow rules;
- создавать независимые тесты материала;
- планировать экспозиции.

### Ограничена

Финальные кадры одной непрерывной последовательности нельзя бесконтрольно распределять между независимыми исполнителями. Разрешено делить только по интервалам между утверждёнными якорями, если:

- все используют один мастер;
- начальный и конечный якоря интервала зафиксированы;
- паспорта и цветовая обработка едины;
- отдельный аудитор собирает участки и проверяет швы.

### Запрещена

- одновременная независимая разработка разных камер;
- параллельное изменение одного `scene_lock`;
- создание финальных кадров до утверждения блокинга;
- независимая генерация каждого кадра без общей сцены;
- слияние результатов без continuity pass.

## 10. Разрешение конфликтов

### Источник против художественного решения

- факт о материале имеет приоритет в реалистической сцене;
- стилизация допустима, если явно записана как решение;
- нельзя приписывать стилизацию источнику.

### Постановка против движения

- если движение не помещается, сначала попытайся перераспределить траекторию и timing;
- если контакт скрыт, постановка должна измениться;
- изменение камеры требует повторного `scene_lock gate`.

### Красивый кадр против continuity

Continuity имеет приоритет. Кадр, который разрушает идентичность или траекторию, пересоздаётся, даже если отдельно выглядит эффектнее.

### Скорость производства против шлюза

Шлюз имеет приоритет. Пропущенный блокинг почти всегда увеличивает стоимость последующего ремонта.

### Разногласие двух источников

Reference Analyst сравнивает условия и степень надёжности. Coordinator не выбирает источник по вкусу без аналитической записи.

---

## 11. Правила повторной попытки

Повторяй локально, если:

- причина дефекта известна;
- есть стабильный предыдущий и следующий якорь;
- `scene_lock` не меняется;
- исправление затрагивает ограниченный интервал.

Возвращайся на этап раньше, если:

- три локальные попытки создают один и тот же класс дефекта;
- исправление требует незапланированной камеры или изменения объекта;
- контакт физически невозможен;
- поиск не дал ответа на материальное поведение;
- downstream-документы противоречат upstream-решениям.

Не делай бесконечные вариации одного кадра без изменения гипотезы. Каждая повторная попытка должна иметь записанную причину и новое ограничение.

## 12. Работа одним агентом

Один агент выполняет роли последовательно и меняет рабочий режим явно:

```text
Режим Source Researcher → создаёт dossier → останавливается на research gate
Режим Reference Analyst → создаёт synthesis → останавливается на synthesis gate
Режим Scene Planner → создаёт blueprint → останавливается на scene lock gate
Режим Motion Planner → создаёт timing sheet и blocking plan
Режим Frame Executor → создаёт кадры и manifest
Режим Continuity Auditor → ищет дефекты, но не оправдывает собственные решения
Режим Final Reviewer → применяет жёсткую карту приёмки
```

При смене режима агент обязан перечитать утверждённые артефакты, а не полагаться на кратковременную память.

## 13. Журнал решений

`change_log.md` содержит только решения, влияющие на воспроизводимость:

- утверждение контракта;
- выбор модели движения;
- фиксация камеры;
- изменение объекта или препятствия;
- изменение timing;
- перевод участка на единицы;
- пересоздание диапазона;
- принятие Minor-отклонения;
- финальное решение.

Пример:

```text
2026-09-01 — Scene Planner — камера зафиксирована: боковой ракурс, наклон вниз 12°.
2026-09-01 — Motion Planner — кадры 57–64 переведены на единицы для точного контакта и снижения стробирования.
2026-09-01 — Continuity Auditor — обнаружен drift длины на u022–u027; диапазон возвращён Frame Executor.
2026-09-01 — Frame Executor — u022–u027 пересозданы от u021 к u027.
2026-09-01 — Final Reviewer — сцена принята, один Minor-дефект края бумаги задокументирован.
```

## 14. Финальный task packet для всей сцены

```yaml
project: Stop-motion Agent Foundations
scene_id: shot01_paper_plane
objective: создать простой трехсекундный план, в котором красный бумажный самолетик перелетает слева направо через синий карандаш, слегка касается его крылом и садится на стол
complexity:
  shots: 1
  primary_actors: 1
  dominant_actions: 1
  camera_moves: 0
  duration_seconds: 3
output:
  aspect_ratio: 16:9
  resolution: 1920x1080
  fps: 24
  output_frames: 72
style:
  medium: материальная stop-motion-анимация
  cadence: двойки с единицами на кадрах 57–64
  imperfection: контролируемая фактура бумаги без случайного мерцания
scene_lock:
  camera: статичная, боковая, наклон вниз 12 градусов
  background: теплый белый стол без рисунка
  light: мягкий слева сверху
  actor: красный бумажный самолетик, постоянная конструкция и метка
  obstacle: неподвижный синий шестигранный карандаш
required_artifacts:
  - scene_contract.md
  - research_dossier.md
  - reference_synthesis.md
  - scene_blueprint.md
  - timing_sheet.md
  - frame_manifest.md
  - blocking_review.md
  - continuity_report.md
  - qc_report.md
acceptance:
```
