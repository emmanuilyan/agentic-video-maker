# Механика, человеческое управление, replay

## Разделение состояния

| Слой | Полномочия |
|---|---|
| Simulation | tick, положение/скорость, коллайдеры, scroll, score, lifeState, obstacle IDs |
| Input | дискретное flap; restart между попытками |
| Level plan | появление и геометрия будущих препятствий; фиксация при spawn |
| Presentation | sprite, palette, фон, декорации, VFX, оформление HUD |
| Editorial | смысловые времена skins и пожелания к событиям |

Монтаж не имеет прямого доступа к hero.y, hero.vy и геометрии активных ворот. Иная реальная механика — отдельная версия правил с видимым переходом и новой проверкой, а не обычный reskin.

## Источник управления

- **Recorded:** доступный реальный поток нажатий с известными начальными условиями. Сохраняет индивидуальный ритм. Не требовать от пользователя сыграть, если ролик заказан автономно.
- **Simulated:** автономный seeded-контроллер выдаёт только нажатия. В метаданных inputSource=simulated; не утверждать, что играл человек.
- **Authored:** вручную заданные flap допустимы для события, их проигрывает общая физика. После редактирования человеческой записи указать mixed и изменённые тики.

Записывать входы, а не рисовать независимую траекторию. Рендер получает рассчитанный массив состояний. Для проверки replay массив заново получают из начальных условий и inputs; сравнение двух копий файла ничего не проверяет.

## Контроллер, похожий на игрока

Модель: **увидел → оценил → решил → дождался реакции → нажал → заметил результат**.

- Наблюдения содержат героя и видимые препятствия в пределах экрана/взгляда. Будущие spawn и скрытые препятствия контроллеру не передавать. Мир может знать их; игрок — нет.
- Логировать observedTick, наблюдаемый obstacle ID, decisionTick, applyTick, действие и причину. Реакция на новое препятствие возможна после его появления в наблюдениях.
- Между наблюдением и действием есть ненулевая настраиваемая задержка. Не пересчитывать старые решения по идеальному текущему состоянию; очередь действий — часть состояния.
- На один проём выбирать немного смещённую цель, устойчивую несколько решений. Не требовать попадания в центр.
- Ритм перемежается короткими поправками и выжиданием. Ошибка имеет последствие и коррекцию. Шум каждого кадра и промах в каждых третьих воротах выглядят искусственно.
- Подбирать достижимые условия/сложность и несколько seed офлайн. Не спасать текущий run невидимой силой или отключением коллизии.

Для первичной настройки можно попробовать решения каждые 3–7 тиков при 60 Hz и реакцию 6–15 тиков, с небольшим смещением цели. Это **гипотезы для playtest**, не научные нормы реакции. Учитывать суммарное запаздывание observation+action queue; при 30 Hz пересчитывать время в тики.

Оценивать 8–12 секунд на скорости 1×: понятна опасность, видна причина поправки, различаются длительности свободного падения. Разброс интервалов flap — диагностика, а не доказательство. Повторные интервалы бывают естественными; не портить хороший проход шумом ради метрики.

## Физика и игровая честность

На фиксированном tick одинаковый flap даёт одинаковый импульс, гравитация объясняет падение. Наклон, сжатие sprite и частицы отображают физику, но не сдвигают коллайдер.

Удар прерывает успешный проход: например, alive → hit → falling → gameOver; прекращаются зачёты ворот, flap не дают обычного управления. Restart допускает сброс счёта явно между попытками. Для непрерывного видео выбрать успешный run.

Счёт растёт один раз, когда задний край препятствия пройден живым героем. Проверять столкновения на тиках, включая промежутки между кадрами; при быстром движении использовать swept-проверку или меньший шаг для исключения пролёта сквозь стену.

Near miss имеет положительный минимальный clearance между коллайдерами по **всей фазе горизонтального перекрытия**, не только в центре ворот. Нулевой/отрицательный clearance — удар согласно правилу контакта, а не повод поправить картинку.

## Герой, уровень, окружение

Все skins используют согласованные pivot и канонический коллайдер. Твёрдый корпус близок к нему; небольшой вылет перьев/эффекта допустим, огромный невидимый зазор — нет.

Пример: птица 64×48 меняется на машину из исходника 140×60 рядом с воротами. Нормализовать/перегенерировать машину в согласованный силуэт; **не увеличивать хитбокс до размера исходного PNG**. Если машина нечитаема, выбрать компактный дизайн. Существующий проём не расширять и не сужать под изображение.

После spawn препятствие сохраняет id, worldX, width, gapY, gapSize, collisionProfile. Верхняя/нижняя картинки крепятся к внутренним краям проёма. Тема может перекрасить активные ворота; новый layout влияет только на будущие, с проверкой достижимости из текущего состояния.

На границе темы сохраняются герой, скорость, scroll, score, active IDs, очередь действий. Одинаковый replay с произвольными skins даёт одинаковую физику. Смена текстуры не сбрасывает фазу параллакса.

## Данные replay

    metadata: schemaVersion, engineVersion, engineHash, runtimeVersion,
              physicsHz, renderFps, seed, durationTicks, initialState,
              inputSource, configHash, obstaclesHash, inputsHash, stateHash
    input: tick, action=flap, source,
           [observedTick, decisionTick, obstacleId, reason]
    obstacle: id, spawnTick, worldX, width, gapY, gapSize, collisionProfile
    state: tick, hero{x,y,vy}, worldX, score, lifeState, activeObstacles, events

События отсортированы; тики целые в пределах run. Повторные flap одного тика нормализовать по правилам ввода и отразить в отчёте. Очередь контроллера сохранять в checkpoint для возобновления генерации; replay использует уже финальные inputs.

state[0] — начальное. input[k] действует на шаге k → k+1. Кадр f показывает state[f × physicsHz / renderFps], когда коэффициент целый. Иначе зафиксировать одну функцию выборки/интерполяции и проверить её. Старый starter с другой семантикой frame 0 адаптировать явно.

Повторяемость гарантировать в зафиксированной среде. Не обещать побитовую идентичность floating-point расчётов на всех платформах без проверки.
